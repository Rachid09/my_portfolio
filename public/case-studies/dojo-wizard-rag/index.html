Dojo Wizard: a guarded, read-only RAG assistant that answers “where is that feature?” inside SecDojo

SecDojo's users kept asking community admins on Discord where features lived and how to use them. I designed and shipped an in-app assistant that answers from the platform's own content, with citations, role-aware retrieval and five layers of guardrails.

01 · Context & goal

Too many features, not enough answers

SecDojo is a cybersecurity training platform serving both individual learners (B2C) and organisations (B2B). It bundles several products: hands-on labs (CyberLab), courses and learning paths (CyberLearn), teams, entities, wallets and certifications, each with its own modules and sub-features.

As the platform grew, users increasingly turned to the community Discord to ask the same questions: where is feature X? how do I create a team? where do I download my VPN profile? Every answer depended on an admin being online.

Before

Support lived outside the product.

User is stuck→Discord→waits for an admin→gets a link

After

Answers live where the question happens.

User is stuck→Dojo Wizard→cited, streamed answer

The goal

Ship an in-app assistant that answers questions about the platform's content and features, not its technical internals, and is safe enough to put in front of every user:

  • Read-only by design. It explains and navigates; it never changes data.
  • Grounded. Answers come from indexed platform content, with citations, or the assistant says it doesn't know.
  • Role-aware. Learners, instructors and admins see different content; lab write-ups (solutions) never reach learners.
  • Native. Streamed in a side panel and a full-page view, light and dark, across SecDojo products.
02 · The product

Dojo Wizard, inside every SecDojo page

A side panel opens from any page; a full-page mode keeps the chat history. Quick actions cover the most frequent questions (creating entities and teams, adding members, wallet and transactions), and users can attach a document to their question.

03 · Architecture

One AI service, hidden behind the platform

The browser never talks to the AI service. The existing Laravel backend authenticates the user, injects their identity and roles, and relays the streamed answer. The AI service owns the models, retrieval, guardrails and chat history.

Why this architecture

Gateway in front of the AI

Reused the platform's existing authentication; the AI service is never exposed publicly.

Identity and roles are set server-side, so neither the client nor the model can choose them.

RAG as a tool, not a pre-step

Gemini decides when to call the search tool, so small talk and follow-ups don't trigger useless retrieval.

Filters and limits are still applied by the server, not by the model.

Qdrant for retrieval

Self-hostable in our Docker stack, fast payload filters for roles and status, and aliases for zero-downtime re-indexing.

Small embedding model

text-embedding-3-small (1536 dims): low cost, strong quality for short, structured platform content.

Streaming with SSE

Token-by-token answers over plain HTTP, easy to relay through the PHP backend and its proxies.

Async ingestion

Content changes are indexed by Celery workers on separate queues, so indexing never slows down chat.

04 · How retrieval works

Index what users read, retrieve only what they may see

The index covers lab descriptions, write-ups, course content and help-center articles: the content users actually navigate. Technical internals are excluded on purpose.

Ingestion: incremental and idempotent

Content eventlab, course or article created, updated or deleted
Sanitisehidden text, scripts and injected instructions removed or quarantined
Chunkby headings, 512 tokens, 64 overlap
Diffcontent hash: unchanged chunks skipped
Embedbatches of 100, retry with backoff
Upsertdeterministic IDs, role + status in payload

Full rebuilds go to a fresh collection and swap an alias atomically, so users never see a half-built index.

Query time: a narrowing funnel

All chunks role, status & language filters
20 candidates cosine similarity
Score ≥ 0.14 off-topic questions stop here
MMR diversity λ = 0.7
Top 5 passages ≤ 3,000 tokens, cited [S1]…

Stage widths are illustrative. If the vector store is unavailable, a keyword fallback answers with the same visibility rules.

05 · Security & guardrails

The model is untrusted. So are the user and the documents.

A cybersecurity audience will try to break an assistant. That's the culture. I treated every input as hostile: the user's message, the indexed documents and the model's own output. Defense in depth meant that when one layer only flagged an attack, the next one still held.

1

Input guard

Normalised every message (Unicode folding, invisible characters removed, letter-spaced text collapsed) and scored injection signals in English and French: instruction overrides, system-prompt extraction, persona and “developer mode” switches, role-tag spoofing, tool escalation, secret requests, exfiltration links. High scores were blocked with a friendly redirect; medium scores ran in a hardened mode without optional tools.

2

Document guard (indirect injection)

At ingestion, stripped what a reader never sees but a model would: HTML comments, scripts, hidden and bidi characters, remote images, non-allowlisted links. Then it quarantined any chunk carrying AI-directed instructions. Because the corpus is about hacking, attack vocabulary (“dump credentials”, “privilege escalation”) was explicitly not treated as an injection.

3

Context isolation

Retrieved passages were wrapped as data with explicit grounding rules; any attempt inside a passage to close that block or impersonate a system or tool message was neutralised before reaching the model.

4

Tool gateway

One choke point between the model and the backend: an allowlist of read-only tools (write tools refused at registration), schema-checked arguments, unknown arguments dropped, a budget of 3 tool calls per turn, and every call audited. Identity and roles were injected from the authenticated session: a model asking for roles: ["admin"] simply had that argument removed.

5

Output guard

A random canary embedded in the system prompt detected prompt leaks; API keys, tokens and private keys were redacted; external images and non-allowlisted links (classic exfiltration channels) were stripped; citations pointing to passages that weren't provided were removed.

06 · My role & actions

What I owned

Lead AI engineer on the AI service (44 of the repository's 76 commits), working with four other engineers.

Chat service

SSE chat endpoint, Gemini and OpenAI providers behind one streaming protocol, file attachments, chat history and feedback, data model and migrations.

RAG pipeline

Ingestion, chunking, embeddings, Qdrant schema and filters, retrieval funnel, the function-calling search tool, evaluation and calibration.

Guardrails

Threat model, the five guard layers, red-team datasets and the regression tests that keep them honest.

Platform integration

A standalone Laravel gateway to prove the end-to-end flow, then integration into the product backends: SSE relay, identity and roles, sessions and files.

Key decisions

  • Read-only scope. The assistant explains and navigates; actions stay in the UI. This removed the riskiest class of tools entirely.
  • Permissions never come from the model. Roles flow from the session token to the retrieval filter, so prompt injection can't widen access.
  • Calibrate, don't guess. The similarity threshold was picked from a measured grid, trading recall against off-topic noise.
  • Domain-aware security. Security content legitimately contains attack vocabulary; guards target instructions aimed at the AI, not topics.

Impact

  • Self-service support in the product. “Where is…” and “how do I…” questions get an immediate, cited answer instead of waiting for a Discord admin.
  • One assistant for every product. The same AI service powers the side panel and full-page chat across SecDojo, CyberLab and CyberLearn.
  • Safe by construction. Read-only tools, server-side permissions and five guard layers let the team expose AI to a hacker audience with confidence.
  • Cheap to keep fresh. Incremental, hash-based indexing re-embeds only what changed; full rebuilds swap in without downtime.
