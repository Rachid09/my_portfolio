AI case study

Dojo Lab Wizard: an AI agent that tells managers exactly which labs to assign, straight from the source of truth

Company managers on SecDojo were guessing which hands-on labs fit their teams. I built, end to end, a lab-finding agent that understands every dimension of the catalog, queries the live database through guarded tools, and drops its picks straight into the assignment or event they are building.

TL;DR

  • Problem: the lab catalog is sliced by lab type, theme, level, topic, MITRE ATT&CK and NICE. B2B managers could not tell which labs matched the skills they wanted to train.
  • Solution: a Gemini function-calling agent that breaks each request into catalog slots, reads the live taxonomy, then queries the database with every slot resolved. It ships as one isolated front-end sidebar, reused in Assign Labs and Host Event.
  • Proof: 15 questions per theme for each lab type. Each question has key answers produced by SQL on the source of truth, and the agent is scored on slots, call order, returned labs and count until it matched. A red team of 24 tool-layer attacks was all neutralised, with 0 legitimate calls denied.

01 · Context & goal

“Which labs should my team do?” had no good answer

SecDojo sells hands-on cybersecurity training to companies. A company manager assigns labs to members and teams, or picks the featured labs of a custom event. The catalog is large and has many dimensions: Offensive, Defensive, AppSec and ICS/OT lab types, each split into themes such as Red Team, Windows/AD, Linux, Network, Web, Cloud or AI, plus difficulty levels, topics, MITRE techniques and NICE skills.

Managers browsed tables and filters, opened labs one by one, and still guessed. A wrong pick meant a training session that missed its goal.

Before

The manager translates a training goal into filters by hand.

Training goal→5 filters + search→open labs one by one→guess

After

The manager states the goal; the agent resolves the filters.

“3 easy Linux labs on privilege escalation”→exact labs→one click to add

The goal

  • Exact, not plausible. Recommendations must equal what the database says, with no invented labs and no padding.
  • Read-only agent, human decision. The agent finds and explains; the manager clicks to add. Assignment stays a UI action.
  • One drop-in feature. The same wizard works wherever a manager chooses labs.
  • Safe tools. Identity, permissions and catalog visibility are enforced by the server, never by the model.
03 · One feature, many pages

An isolated wizard any page can borrow

I built the wizard as a self-contained front-end sidebar, mounted once at the application root and driven by a shared service. A host page only does two things: open the wizard and listen for selected labs. Selection state is shared both ways. When the manager removes a lab on the page, its card in the wizard flips back to Add.

The same component powers direct assignment to members and teams, the featured labs of a custom event, and any other page where a manager picks labs can mount it the same way. There is no copy-paste and no per-page AI code.

04 · Architecture

The model proposes, the platform decides

The browser never talks to the AI service. Laravel authenticates the manager, overwrites identity and roles from the session, and relays the stream. The FastAPI agent runs the Gemini function-calling loop, but every tool call goes through a gateway and ends at the platform's own lab API. That API applies the same visibility rules as the product.

Database, not embeddings, for structured asks

“3 easy Linux labs” has one correct answer, and SQL already knows it. The agent's job is to translate the request into filters. Retrieving “similar” text would only approximate it.

Reuse the platform's rules

Lab visibility (public, active, plan-specific catalogs) lives in one place, the lab API. The agent inherits it instead of re-implementing it.

A manual tool loop

I ran the function-calling loop myself instead of letting the SDK auto-execute. That made room for the gateway checks, streaming tool progress to the UI, and a hard step cap.

Structured cards, not parsed prose

Tool results stream to the UI as a tagged JSON payload that renders as lab cards. The text answer and the data cannot drift apart.

05 · How the agent thinks

Every word can be a filter, so count the slots first

One sentence often carries several parameters, and each one maps to a different filter. The change that mattered most was making the catalog's segmentation explicit to the model: five slots, the parameter each one feeds, the valid values (read live from the taxonomy and cached), and a fixed call order.

06 · Security

Tools are where an agent gets dangerous, so I guarded the tools

A chatbot that only talks can leak words. An agent that calls functions can leak data. I treated the model as untrusted: it may propose a call, and the platform decides whether it runs and with which arguments.

1

Authenticated entry

Only Laravel can reach the agent. It checks the JWT and overwrites user ID and roles from the session, so whatever the browser sends is ignored.

2

Surface allowlist + role gate

The assignment wizard exposes two read-only tools, nothing else. Assignment surfaces open only for manager roles. Write tools are refused at registration.

3

Server-side identity in every call

The gateway injects the user ID into each tool call. IDs or roles proposed by the model are dropped and logged as forged.

4

Argument contracts

Unknown arguments are dropped, and types, lengths and list sizes are capped. Levels, lab types, themes and topics must exist in the live taxonomy, and invalid values come back with the allowed list so the model can self-correct. The lab API validates again behind the gateway.

5

Injection screening, both directions

Free-text arguments are scored for prompt injection before they reach the API. Lab descriptions coming back are sanitised, and any that carry instructions are withheld.

6

Call order and budgets

A search needs a taxonomy read earlier in the turn. Per-tool and per-turn budgets plus a 10-step cap stop loops.

7

Visibility at the source

The lab API returns only public, active labs, and the next-generation catalog only to companies whose plan enables it. The model cannot ask its way around this.

8

Answer grounding

Lab references in the final answer must come from this turn's results and never exceed the requested count. Hallucinated IDs are stripped.

07 · Evaluation

Graded against the database, question by question

“Looks right” is not a metric for a recommender that managers trust with training budgets. I built a test suite in which every question has a key answer computed from the database itself, then scored the agent on each step of its reasoning, not just the final text.

2 · Key answers from the source of truth

For each question I wrote down the slots a correct agent must extract. Then I ran those slots as a real query on the production tables, with the same visibility rules as the product: public, active, not guided. The result is the list of correct labs, the key answer. Because there are often more valid labs than requested, a recommendation is correct when every lab is in the key list and the count equals the request, or fewer if fewer exist.

Question→Gold slots→SQL on source tables→Key answer⇄Agent trace: slots · calls · labs→Scores

3 · What gets scored

Slot precision & recall

Did it extract every parameter in the question, and nothing invented?

Call order

Taxonomy first, then one search with all slots, with no unnecessary tools.

Result precision

Share of recommended labs that are in the key answer.

Count compliance

Exactly what was asked, or fewer if fewer exist. Never padded.

Exact match

All of the above perfect. This is the number I iterated on.

5 · The iteration loop

Each run produced a list of failing questions. I grouped them by failure mode and fixed the cause in the instructions, the tool contracts, the API or the knowledge the model sees. Then I reran the full matrix until the agent's answers matched the key answers.

08 · My role & decisions

One owner, every layer

I designed and built the feature end to end:

  • the front-end sidebar and shared selection service, plus their integration into Assign Labs and Host Event
  • the Laravel gateway and the internal lab API the agent queries
  • the FastAPI agent, its tools and the tool gateway
  • the evaluation suite

The agent reads, the human assigns

No write tools. Assigning training to people stays a deliberate click, which removed a whole class of risk.

Truth from SQL, language from the LLM

The model translates intent into filters; the database decides what is correct. Hallucinated labs became structurally impossible.

Build once, host anywhere

An isolated component behind a two-method contract turned one AI feature into a capability for every lab-picking page.

Measure what can be wrong

Scoring slots, call order, results and count separately showed where the agent failed, so every iteration fixed a cause, not a symptom.
